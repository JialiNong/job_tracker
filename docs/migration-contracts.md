# Migration safety net (phase 0)

The Tracker is being rewritten as Next.js + PostgreSQL. Before any of that
code exists, two suites pin down what the current app does, so the new one
can be checked against it instead of by eye.

## 1. API contract snapshots — `tests/contract/`

| File | What it is |
|---|---|
| `fixture.json` | Portable dataset (Mongo Extended JSON). Synthetic: no real companies, notes or answers. Generated by `build_fixture.py`. |
| `cases.json` | 54 requests: every read endpoint plus the main writes (status, timeline, notes, highlights, Q&A, info, link, delete, Unmatched, Timeouts, Log Job, agent push). |
| `snapshots/` | The current Flask app's normalised JSON for each case. |
| `run_contract.py` | Runner. Talks HTTP only, so it can check any server. |
| `mongo_seed.py` | Loads the fixture into Mongo (current stack). |

```bash
./scripts/run_contract.sh                # Flask app vs snapshots
./scripts/run_contract.sh -k jobs-       # only matching cases
./scripts/run_contract.sh --update       # rewrite snapshots after an intended change
./scripts/run_contract.sh --base-url http://127.0.0.1:3000 --seed-cmd "pnpm contract:seed"
```

How a run stays deterministic:

- **Pinned clock.** The server runs with `TRACKER_ALLOW_FIXED_NOW=1`,
  `TRACKER_FIXED_NOW=<fixture.now>` and `TZ=Europe/Berlin`. Every "now" in
  the web, core and services layers goes through `src/core/clock.py`. The
  pin is ignored unless the allow flag is set, so production cannot freeze.
- **Fresh data before every write.** After any non-GET case the database is
  reseeded from the fixture.
- **Normalised ids.** Fixture ids appear as `{matched_jobs:5}`; ids created
  during a case become `<new-id-1>`, `<new-id-2>` in order of appearance.
  Object keys are sorted.

What the new stack has to provide to run against these snapshots:

1. The same routes, request bodies and JSON shapes.
2. A seed command that loads `fixture.json` (path in `CONTRACT_FIXTURE`) into
   its database, keeping the fixture's 24-hex ids as primary keys.
3. The same login form (`POST /login`, fields `username`, `password`) and
   the two clock variables above.

## 2. Browser e2e — `tests/e2e/`

24 tests click through the real pages. They no longer call the Mongo driver:
all seeding and checks go through a store object in `harness.py`
(`MongoStore`: `seed`, `tracker_job`, `scraped_job`, `timeout_job`, ...).

```bash
./scripts/run_e2e.sh                                     # Flask + MongoStore
E2E_STORE=pg_store:PostgresStore E2E_BASE_URL=http://127.0.0.1:3000 ./scripts/run_e2e.sh
```

The new stack adds a store class with the same method names over Postgres.

## Known issue found while pinning the clock

The current code mixes naive local time (`clock.now()`) and naive UTC
(`clock.utcnow()`): Log Job without a date, link replacement, and the
details / AI save paths stamp UTC; everything else stamps local time.
GitHub Actions runs with `TZ=Europe/Berlin`, Render with UTC. The same field
can therefore be one or two hours apart depending on where it was written,
and a job logged just after midnight lands on the previous day in the
heatmap. Phase 0 keeps this behaviour (the snapshots record it). The
Postgres schema fixes it with `timestamptz` columns and one rule for
writing times.
