# PostgreSQL schema

Schema: `packages/db/prisma/schema.prisma`. The same thing as SQL:
`packages/db/prisma/migrations/*_init/migration.sql` (generated by Prisma).
Numbers below come from the live Atlas data on 2026-11-19. Review decisions
taken on 2026-11-19 are marked **(decided)**.

## Mongo to Postgres at a glance

| Mongo | Postgres | Rows today |
|---|---|---|
| `jobs` + `matched_jobs` | `jobs` (the posting) and `applications` (Tracker card) | 2,139 jobs, 755 applications |
| AI fields on both | `job_analyses` (one row per run) | ~2,080 runs (only the latest survives in Mongo) |
| `matched_jobs.application_timeline` | `application_events` | ~450 |
| `timeout_jobs` | `scrape_timeouts` | 28 |
| `scraper_stats` | `scraper_daily_stats` + `scraper_totals` | 31 + 1 |
| `company_profiles` | `company_profiles` | 105 |
| `stats_cache` | `stats_cache` | 1 |

```
company_profiles 1 ──< job_analyses >── 1 jobs 1 ── 0..1 applications 1 ──< application_events
                                          └── current_analysis_id ──> job_analyses (latest run)
```

## Decisions

**D1. One posting, one Tracker card: `jobs` 1 — 0..1 `applications`. (decided: split now)**
Every one of the 755 `matched_jobs` documents has a twin in `jobs` with the
same `(source, job_id)`: a full copy of the posting plus tracking fields.
The copies differ (company on 29, location on 48) because company names and
locations are cleaned up by hand on the Tracker: legal suffixes removed so
"Seen this company before" groups every posting of a company, and
locations fixed so the "Where you applied" chart counts cities correctly.
Those edits only reached the Tracker copy; anything reading `jobs` still
saw the raw value. With one row per posting, an edit lands in the only
copy. `applications.job_id` is unique, so a posting has at most one card.

- Hand-edited fields are listed in `jobs.manual_fields`; a re-scrape keeps them.
- `jobs.dedup_key` keeps the title + company *as scraped* and is not
  recomputed after an edit, so a later scrape of the same posting still
  matches it.
- *Migration:* where twins disagree, the `matched_jobs` value wins, and
  that field is added to `manual_fields`. Every conflict is listed in the
  migration report.

**D2. Every AI run is kept: `job_analyses`. (decided: keep history)**
A job can be analysed more than once (pipeline, Run AI after a re-fetch,
agent push). Each run inserts a row; `jobs.current_analysis_id` points at
the latest, and that row is what the Tracker and Unmatched pages show.
Mongo only kept the latest result, so the migration creates one run per
analysed job (`trigger = 'migration'`). `model` and `prompt_version` are
recorded for new runs, which makes "did the new prompt score differently?"
answerable later.

**D3. Keep the Mongo ObjectId hex as the primary key (`char(24)`).**
Deep links (`/?open=<id>`), links inside sent Telegram messages, and the
contract snapshots all carry these ids. New rows get a fresh 24-hex id
from the app, so ids keep one format. Internal rows nobody links to
(`job_analyses`, `application_events`) use `bigint` identity keys.

**D4. Columns for what is filtered or sorted, JSONB for what is only shown.**
Columns on `job_analyses`: `match_score`, `match_gate`, `recommendation`,
`summary`, `disqualification_reason`, `analyzed_at`. JSONB `details`:
reasons, missing requirements, red flags, the two matched/unmatched
breakdowns, `requirement_extract`, `job_labels`. Their shape changes with
the prompt, and nothing queries inside them. `application_qa` is JSONB for
the same reason. The Unmatched page filters on the latest run's score
through `current_analysis_id` (a join; ~2k rows, indexed).

**D5. `applications.applied_at` stays a column next to the events. (decided)**
The heatmap, the "applied on" filter and list sorting all key on it. It is
written in the same transaction as the events. The migration checks that
it equals the first `applied` event (or the old value when there is no
timeline) and reports mismatches.

**D6. Enums for closed vocabularies, text for open ones.**
`status`, timeline `step`, `origin` and `analysis_state` are enums: the
code branches on every value, and a typo should fail at write time.
`source` stays text: new sources are added often.

**D7. `jobs.analysis_state` replaces three things.**
- `jobs.status = "new"` (queue marker for "not analysed yet"): `none`
- `ai_pending` (saved link-only): `pending`
- the in-memory Run AI lock: `running` + `analysis_started_at`

Taking the lock is one conditional `UPDATE ... WHERE analysis_state <>
'running' OR analysis_started_at < now() - interval '5 minutes'`, so it
works across serverless instances and recovers from a crashed run.

**D8. A posting seen through two sources is one job. (decided)**
`posting_key` (derived from ATS / career-site URLs, e.g.
`personio:bookboost:2811207`) is unique. When a second source finds a
posting whose key already exists, it attaches to that job instead of
creating a row. LinkedIn and Indeed have no `posting_key` (their job id is
the posting id), so `(source, external_id)` stays unique too. Today 200 of
2,139 jobs have a key and exactly one key appears twice (a manual log and
an ATS scrape of the same Personio posting); the migration merges those
two, and the one `(source, job_id)` duplicate in `jobs`.

**D9. Scraper counters: daily rows plus one totals row.**
The all-time counters (6,709 clicked) predate the daily documents (31
days), so totals cannot be summed from the days.

**D10. Time: `timestamptz` everywhere, one rule for writing.**
Today naive local times and naive UTC times are mixed (see
`docs/migration-contracts.md`), and Render runs in UTC while GitHub Actions
runs in Europe/Berlin. New rule: store instants (`now()`), and turn them
into calendar days only with `AT TIME ZONE 'Europe/Berlin'` (heatmap,
"applied on", weekly bars). User-picked dates ("applied on 12 Nov") are
read as Berlin wall time.
*Migration:* old naive values are read as Berlin wall time, except
`link_replaced_at` and `details_fetched_at`, which are always UTC. Values
written by the web app on Render are UTC and cannot be told apart; they
end up at most two hours off, and only `updated_at` and some web-entered
timeline times are affected.

**D11. Dropped on purpose.**
- `jobs.status` (`new` / `pending` / `applied` / `Viewed`): replaced by
  `analysis_state` and `applications.status`.
- The copied posting fields in `matched_jobs` (D1).
- The per-job `company_profile` snapshot (D13).
- `company_profiles._model` / `_usage`: become `model` / `usage`.

**D12. Two connection strings.**
`DATABASE_URL` is Neon's pooled endpoint (serverless functions open many
short connections). `DIRECT_DATABASE_URL` is the direct one, for migrations
and the long-running pipeline.

**D13. An analysis references the company profile it used. (decided)**
Instead of copying the profile into every job, `job_analyses.company_key`
is a foreign key to `company_profiles.key`. The key is stored at analysis
time, not derived from `jobs.company` when reading: company names get
edited by hand (D1), and re-deriving the key from the edited name would
point at a different profile, or none. Today the snapshots and the cache
agree: every snapshot whose company has a cache row has the same text.
One Tracker job (ContractHero) has no cache row under its current name and
four snapshots belong to jobs with an empty company; the migration report
lists them, and the ContractHero profile is recreated from its snapshot.

## Running the migration

Local Postgres runs in Docker (`docker-compose.yml`, port 54329) with two
databases: `tracker_dev` (real data) and `tracker_test` (fixtures).

```bash
pnpm install
pnpm db:up                                # start Postgres
pnpm db migrate:deploy                    # create the tables
pnpm db from-mongo --dry-run              # transform + report, write nothing
pnpm db from-mongo                        # replace tracker_dev with the Mongo data, then verify
pnpm db test                              # unit tests (time, company key, transform rules)
DATABASE_URL=postgresql://tracker:tracker@127.0.0.1:54329/tracker_test pnpm db contract:seed
```

- `from-mongo` only reads Mongo (`MONGO_URI` from the repo's `.env`) and
  replaces every Postgres table in one transaction, so it is safe to run
  daily during the parallel week. The full report (merges, Tracker edits
  kept, suspicious scraped companies) is written to `packages/db/reports/`,
  which git ignores because it contains job data.
- After loading it checks the result against the raw Mongo documents
  (`src/verify.ts`): row counts, every Tracker card's status, applied date,
  notes, shown title/company/location and timeline, every current AI
  score, and the uniqueness rules.
- `contract:seed` loads `tests/contract/fixture.json` through the same
  transform and refuses any database whose name does not end in `_test`.

First run on the live data (2026-11-19): 2,137 jobs, 754 applications,
1,882 analyses, 454 timeline events; all checks passed, and applications
per Berlin day over the last 120 days equal the current heatmap's numbers.
